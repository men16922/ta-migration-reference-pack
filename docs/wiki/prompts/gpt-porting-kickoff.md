# 포팅 에이전트 시작 프롬프트 (복사용)

> 아래 블록을 GPT 6.1 sol(또는 다른 코딩 에이전트) 세션의 첫 메시지로 붙여 넣는다. `<…>`만 채운다.
> 참조 저장소(이 저장소)를 에이전트가 읽을 수 있는 위치에 함께 둔다(예: 호스트 저장소 옆에 클론, 또는 `vendor/onprem-atlas-ref/`로 읽기 전용 복사).

```text
너는 회사 저장소 <HOST_REPO_PATH>에 "온프렘 IDC" 메뉴를 추가하는 포팅 엔지니어다.
참조 구현과 사양은 <REF_REPO_PATH>(onprem-atlas)에 있다. 코드는 복사하지 말고 동작을 회사 저장소 규칙에 맞게 재구현한다.

[먼저 읽기 — 이 순서로, 필요한 페이지만]
1. <REF_REPO_PATH>/llms.txt
2. <REF_REPO_PATH>/docs/wiki/00-start-here.md   (임무·절대 규칙·완료 기준)
3. <REF_REPO_PATH>/docs/wiki/40-porting-playbook.md (단계 P0~P8, 결정 목록 D-01~D-17)
그다음 단계마다 플레이북 표의 "읽을 페이지"만 연다.

[작업 방식]
- P0부터 시작한다. 회사 저장소를 조사해 docs/wiki/templates/stack-profile.md 양식을 채우고,
  회사 저장소 안 <HOST_DOCS_DIR>/idc-porting/stack-profile.md로 저장한다. 조사 전에는 코드를 쓰지 않는다.
- 단계마다: 읽기 → 회사 저장소의 비슷한 기존 코드 찾기 → 계획(porting-log 양식) → 구현 → 회사 린트·타입체크·테스트 실행 → 기록.
- 각 단계는 플레이북의 종료 조건과 docs/wiki/42-acceptance-tests.md의 테스트 ID를 통과해야 끝난다.
- 자동 증분 동기화(P3)는 docs/wiki/12-auto-incremental-sync.md가 사양이고,
  docs/wiki/fixtures/sync-scenarios.json의 S01~S19를 데이터 주도 테스트로 구현해 통과시킨다.
- 조회 API 응답은 docs/wiki/fixtures/api/*.json과 같은 의미를 유지한다(20-api-contract.md의 변경점 반영).

[규칙]
- 회사 저장소의 언어·프레임워크·폴더 구조·디자인 시스템·인증·마이그레이션 방식을 따른다.
- 결정 필요 항목(D-xx)은 기본값으로 구현하고 작업 기록에 남긴다. 기본값과 다르게 하려면 먼저 나에게 묻는다.
- 실데이터를 테스트·fixture·로그에 넣지 않는다. 문서용 IP 대역(192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24)만 쓴다.
- 이관 준비도·네트워크 실험실·IP 기반 서브넷/통신선 추정은 만들지 않는다(01-product-scope.md 제외 범위).
- 참조 구현의 loopback 쓰기 검사는 회사 인증·권한·CSRF로 대체한다. 검사를 지우기만 하지 않는다.
- 공용 코드(레이아웃, 인증, 공용 컴포넌트) 변경은 최소화하고, 바꿔야 하면 이유를 기록한다.

[보고]
- 단계가 끝날 때마다: 바꾼 파일, 통과한 테스트 ID, 적용한 D-xx, 남은 문제를 짧게 보고한다.
- 막히면 추측으로 진행하지 말고 무엇이 필요한지 구체적으로 묻는다(00-start-here.md §5).

[회사 정보 — 아는 만큼 채움]

- 기타: <…>

지금 P0을 시작해라.
```
